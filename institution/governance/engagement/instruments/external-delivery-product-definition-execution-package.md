  <mission>
    Develop the bounded Generation One Headquarters product definition necessary to operationalize Huerta Group LLC's accepted External Delivery Capability Network &amp; Implementation Scoping / Sourcing operating model.

    The product definition must establish the minimum coherent Headquarters capability across three related layers:

    1. Capability Network
    2. Implementation Scoping &amp; Sourcing
    3. External Delivery Assignment

    The result must be sufficiently precise for Founder Office product acceptance and subsequent technical routing to Platform &amp; Systems Development.

    DO NOT IMPLEMENT CODE.

    DO NOT prescribe database tables mechanically from conceptual nouns.

    DO NOT invent legal, accounting, procurement, client-authority, commercial, or institutional doctrine beyond the Founder-authorized model.
  </mission>

  <product_objective>
    Enable Huerta Group Headquarters to institutionalize external delivery capability while progressively reducing unnecessary dependence on Founder-performed execution.

    Preserve Huerta Group discretion over how work is delivered.

    External execution is:
    - an ordinary first-class delivery option;
    - not an exception;
    - not mandatory;
    - not automatically selected.

    The product should help Headquarters answer:

    Can qualified external capability perform this requirement to Huerta Group's required standard under acceptable economics, control, confidentiality, risk and accountability?
  </product_objective>

  <controlling_architecture>
    Define the product around:

    CAPABILITY NETWORK
    →
    IMPLEMENTATION SCOPING &amp; SOURCING
    →
    EXTERNAL DELIVERY ASSIGNMENT
    →
    PROVIDER PERFORMANCE LEARNING

    Preserve the semantic sequence:

    Provider knowledge informs sourcing.

    Sourcing informs delivery architecture.

    Delivery architecture may inform commercial decision-making.

    Commercial decision ≠ client authorization.

    Authorized Work permits bounded execution.

    External assignment connects a provider to authorized work.

    Provider completion ≠ Huerta Group acceptance.

    Huerta Group acceptance ≠ Client Deliverable.

    Client Deliverable ≠ client acknowledgement.

    Actual external execution produces evidence that may improve future provider knowledge.

    No transition automatically creates the next state.
  </controlling_architecture>

  <required_conceptual_records>

    A. independent persisted primitive;

    D. derived state;
    E. no separate representation.

    Explain the semantic reason for the determination.

    Do not mechanically create one database table per conceptual noun.
  </required_conceptual_records>

  <layer_1_capability_network>

    <purpose>
      Establish durable institutional operating knowledge and evidence concerning external individuals and organizations that may provide delivery capability.
    </purpose>

    <provider_model>
      Support:
      - individual freelancers;
      - independent specialists;
      - businesses;
      - agencies;
      - professional firms;
      - other legitimate external delivery organizations.

      Provider type is descriptive.

      Provider type MUST NOT establish:
      - quality;
      - preference;
      - qualification;
      - maturity;
      - approval.
    </provider_model>

    <incomplete_records>
      Incomplete provider records are legitimate.

      Unknown must remain representable.

      Do not require Headquarters to know every field before a provider can enter the network.

      A provider may be useful before:
      - pricing is known;
      - every capability is known;
      - formal evaluation exists;
      - a test exists;
      - client work has occurred.
    </incomplete_records>

    <discovery_provenance>
      Preserve how a provider was discovered.

      Examples may include:
      - referral;
      - personal relationship;
      - Tucson Digital Deals participation;
      - marketplace presence;
      - internet research;
      - prior operating relationship;
      - direct outreach;
      - other source.

      Discovery source ≠ qualification.

      Tucson Digital Deals participation ≠ Huerta Group qualification.

      Personal relationship ≠ Huerta Group qualification.

      Referral ≠ Huerta Group qualification.

      Marketplace presence ≠ Huerta Group qualification.

      Do not design TDD integration.
    </discovery_provenance>

    <network_workflow>
      Product definition must support authentic network development:

      Discover
      →
      Record
      →
      Characterize Capability
      →
      Gather Evidence
      →
      Evaluate
      →
      Optional Test
      →
      Actual Use
      →
      Learn

      This is an operating progression, not a mandatory lifecycle engine.

      A provider need not traverse every step before being recorded or considered.
    </network_workflow>

  </layer_1_capability_network>

  <capability_specific_evidence_and_maturity>

    <maturity_model>
      Preserve the accepted capability-maturity concept:

      Discovered
      →
      Evaluated
      →
      Tested
      →
      Proven
    </maturity_model>

    <critical_rule>
      Maturity is:
      - evidence-based;
      - contextual;
      - capability-specific;
      - reversible.

      Do NOT model a provider as universally Proven.
    </critical_rule>

    <capability_specificity>
      The same provider may legitimately be:
      - Proven for Capability A;
      - Tested for Capability B;
      - Evaluated for Capability C;
      - merely Discovered for Capability D;
      - Unknown for Capability E.

      Product definition must preserve these distinctions.
    </capability_specificity>

    <historical_evidence>
      Historical evidence must remain durable even when current sourcing posture or evaluation changes.

      Current interpretation must not destructively rewrite historical evidence.
    </historical_evidence>

    <provider_summary>
      If a provider-level summary or sourcing posture is useful, define it as derived or explicitly subordinate to capability-specific evidence.

      It must not obscure capability-level differences.
    </provider_summary>

    <prohibited_ratings>
      Do not create:
      - public scores;
      - star ratings;
      - universal numerical rankings;
      - approved-vendor badges;
      - simplistic permanent provider grades.
    </prohibited_ratings>

    <required_definition>
      Define:
      - what evidence can support each maturity state;
      - how maturity is determined;
      - how maturity can regress/change;
      - how evaluation differs from raw evidence;
      - how testing differs from actual client use;
      - how actual successful use contributes evidence without automatically proving universal capability.
    </required_definition>

  </capability_specific_evidence_and_maturity>

  <provider_evidence>
    Define the minimum durable evidence architecture.

    Provider Evidence should be capable of representing evidence such as:
    - discovery/provenance;
    - portfolio/work sample;
    - reference;
    - credential/license information where relevant;
    - bounded Huerta Group test;
    - quotation/proposal interaction;
    - prior operating observation;
    - actual assignment performance;
    - security/access behavior;
    - other capability-relevant evidence.

    Evidence existence does not itself establish qualification.

    Preserve:
    - provider;
    - applicable capability where relevant;
    - evidence type;
    - context;
    - source/provenance;
    - observation/reference;
    - relevant date/time;
    - recorder provenance;
    - durable historical integrity.

    Do not invent a generalized document-management system.
  </provider_evidence>

  <provider_evaluation>
    Define Provider Evaluation as a deliberate Huerta Group interpretation of available evidence for sourcing purposes.

    Evaluation should be capable of expressing:
    - capability being evaluated;
    - evidence considered;
    - current maturity/posture;
    - strengths;
    - limitations;
    - material unknowns;
    - risk considerations;
    - evaluator;
    - evaluation time;
    - rationale.

    Evaluation ≠ evidence.

    New evaluation ≠ destruction of old evidence.

    Current sourcing posture may change.

    Preserve historical evaluation/evidence sufficiently for institutional learning.

    Do not create permanent simplistic ratings.
  </provider_evaluation>

  <bounded_non_client_testing>
    Define how Headquarters may represent an optional bounded non-client provider test.

    A test:
    - is capability-specific;
    - has a defined purpose;
    - has a bounded test requirement;
    - has an observed result;
    - produces Provider Evidence;
    - may influence maturity;
    - is not client work;
    - is not an External Delivery Assignment;
    - does not create client authority;
    - does not automatically establish Proven status.

    Avoid creating a generalized testing platform.
  </bounded_non_client_testing>

  <layer_2_implementation_scoping_sourcing>

    <purpose>
      Establish a bounded Opportunity/Engagement-specific operating capability for determining what contemplated implementation requires, how it may be delivered, what external capability/cost/risk is involved, and whether Huerta Group possesses sufficient information for a commercial decision.
    </purpose>

    <origin>
      Implementation Scoping &amp; Sourcing must be capable of originating from appropriate existing Headquarters context including Possible Work and, where applicable, Engagement context.

      OSA MUST NOT be required as the originating path.
    </origin>

    <workflow>
      Support:

      Contemplated Implementation
      →
      Define Outcome
      →
      Decompose Requirements
      →
      Identify Required Capabilities
      →
      Determine Candidate Delivery Methods
      →
      Resolve Material Unknowns
      →
      Source/Evaluate Resources where necessary
      →
      Discover Costs/Dependencies/Risks
      →
      Determine Delivery Architecture
      →
      Determine Commercial Readiness
      →
      Founder Commercial Decision / Commercial Proposal path
      OR
      Do Not Pursue

      Treat this as bounded operating workflow, not generalized workflow-engine doctrine.
    </workflow>

    <implementation_requirement>
      Define the minimum representation of an Implementation Requirement.

      It should allow contemplated implementation to be decomposed into bounded requirements sufficiently to establish:
      - required outcome/component;
      - required capability/capabilities;
      - relevant constraints;
      - dependencies;
      - material unknowns;
      - candidate delivery methods;
      - external-resource need where applicable;
      - sourcing status;
      - expected economics where known;
      - risk/control considerations.

      Determine whether Implementation Requirement requires an independent persisted primitive or a bounded child/relationship within Implementation Scoping &amp; Sourcing.

      Explain the choice.
    </implementation_requirement>

    <required_capability>
      Required Capability should reuse or relate to the Capability Network where faithful.

      Do not create a second incompatible capability taxonomy solely for implementation scoping.

      Preserve the distinction between:
      - capability needed by the contemplated implementation;
      - provider claiming/possessing capability;
      - evidence establishing provider capability.
    </required_capability>

    <candidate_resource_consideration>
      Define the minimum representation needed to associate candidate external resources with a specific requirement.

      Candidate consideration should support:
      - provider;
      - relevant provider capability;
      - requirement;
      - reason considered;
      - current suitability posture;
      - material unknowns;
      - quotation/economic information where applicable;
      - risk/dependency observations;
      - selected/not selected/not yet determined as appropriate.

      Candidate consideration ≠ provider qualification.

      Candidate consideration ≠ assignment.

      Candidate consideration ≠ automatic selection.

      Determine whether this is best represented as a persisted relationship rather than an independent top-level primitive.
    </candidate_resource_consideration>

  </layer_2_implementation_scoping_sourcing>

    <first_class_external_path>

  <material_unknowns>
    Unknown must be first-class in Implementation Scoping &amp; Sourcing.

    The product must allow Headquarters to distinguish:
    - information known;
    - information not yet known;
    - unknowns material to delivery architecture;
    - unknowns material to commercial readiness;
    - unknowns requiring provider research;
    - unknowns requiring professional scoping.

    Do not convert missing information into false certainty.

    Preserve the institutional read-fidelity principle conceptually:

    UNKNOWN ≠ NONE

    UNRESOLVED ≠ NEGATIVE

    INFORMATION NOT YET OBTAINED ≠ INFORMATION DOES NOT EXIST
  </material_unknowns>

      - software/direct costs;
      - known delivery dependencies;

    </historical_truth>

  </proposal_economics>

  <ordinary_proposal_vs_paid_scoping>

    <substance_test>
      Preserve the accepted substance test.

      Ordinary proposal development may include:
      - reasonable research;
      - straightforward provider quotations;
      - software-price checking;
      - similar work principally necessary to price understandable implementation.

      Paid scoping becomes appropriate when reliable pricing requires material professional analysis necessary to determine what the solution itself should be.
    </substance_test>

    <no_threshold>
      Do NOT establish:
      - fixed hours;
      - fixed fee;
      - fixed dollar threshold;
      - universal complexity score;
      - automated threshold formula.
    </no_threshold>

    <product_requirement>
      Headquarters must permit an explicit disposition that implementation cannot responsibly become proposal-ready without separately authorized paid scoping.

      Define how this should appear in Implementation Scoping &amp; Sourcing.

      This disposition must not automatically:
      - create paid work;
      - create a Commercial Proposal;
      - create an Engagement;
      - create Authorized Work;
      - establish client acceptance.
    </product_requirement>

  </ordinary_proposal_vs_paid_scoping>

  <commercial_readiness>

    <definition>
      Define Commercial Readiness as a sourcing/scoping determination that sufficient implementation information exists for Founder commercial decision-making.

      Commercial Readiness ≠ Commercial Proposal.

      Commercial Readiness ≠ Founder approval.

      Commercial Readiness ≠ client acceptance.

      Commercial Readiness ≠ implementation authorization.
    </definition>

    <required_state_model>
      Define the smallest useful state/disposition model capable of distinguishing at minimum:

      - work being scoped;
      - unresolved sourcing/information;
      - sufficient information for Founder commercial decision;
      - paid scoping indicated;
      - do not pursue.

      Use concise operator language.

      Avoid a generalized sales pipeline.
    </required_state_model>

    <timestamps>
      Preserve enough timestamps to learn authentic elapsed sourcing/scoping time later.

      No standardized sourcing/scoping turnaround currently exists.

      Do not invent an SLA.
    </timestamps>

  </commercial_readiness>
